## 0. 共享上下文（每个新任务都建议先读这一节）

### 0.1 产品目标与业务闭环

面向电商运营团队的智能运营工作台，以单品全生命周期为核心：

```
商品建档与竞品录入 → 智能诊断 → 创意方案生成 → 异步素材制作与审核
→ 投放策略建议与人工确认 → 经营数据回填 → 闭环复盘报告 → 行动项转入下一轮诊断
```

两条硬性合规边界：

- 平台账号只保存接入标识与脱敏授权状态，严禁存储明文密码或 Cookie。
- 投放建议只作为决策参考，严禁调用外部广告接口自动创建计划或扣费。

业务范围同时覆盖实物商品与本地生活服务（除甲醛、洗衣店）。服务业务复用同一套闭环，差异通过服务配置、内容口径与素材模板表达，详见 0.10。

### 0.6 状态机与派生规则

**任务状态**（M3 实现）

```
pending → running → succeeded | failed | timeout
pending / running → cancelled
failed / timeout → retry（新 attempt）→ pending
```

- 心跳超时由巡检线程判 `timeout`；重试次数上限 `max_retry`。
- 默认参数：图片超时 300s、视频超时 600s、最大重试 2、并发 2（可配置）。
- 允许配置模拟耗时区间与模拟失败率，保证演示可复现。

**素材状态**（M3）

```
pending_review → approved | rejected；approved → archived
```

**投放建议状态**（M4）

```
draft → pending_approval → approved | rejected
rejected → draft（修改后重提）
approved → closed（投放周期结束、数据回填后）
```

- 高风险判定：预算 ≥ `risk.high_risk_budget`（默认 5000）或命中配置规则。
- 高风险只能由 `manager` 审批；低风险可由 `operator` 确认。

**商品闭环阶段**（M1 已实现，`app/services/lifecycle.py` 派生）

```
draft 建档中 → diagnosed 已诊断 → creative_ready 创意就绪 → asset_ready 素材就绪
→ launching 投放中 → reviewing 复盘中 → reviewed 已闭环
```

**诊断版本**（M2 实现）

- 每次生成 v1、v2…；仅一条 `status=current`，历史保留。
- 复盘行动项触发的诊断携带 `source_report_id`，并预填上一轮结论。

### 0.8 全局约定

- 全站中文 UI，金额 `¥`，日期 `YYYY-MM-DD`，时间 ISO 字符串。
- REST 前缀 `/api`，JSON 字段 snake_case，JWT 放 `localStorage`。
- 任务状态前端 2 秒轮询，不使用 SSE/WebSocket。
- 素材文件由后端静态挂载 `/files`，数据库存相对路径（如 `/files/assets/xxx.svg`）。
- AI 生成内容必须结构化、可编辑、可确认/归档，禁止只读。
- 不接真实竞品爬虫；「智能解析」只处理用户粘贴的文本。
- 不引入 Redis / Docker / Celery；队列用 SQLite 表 + 应用内 worker 线程。
- 每完成一个里程碑：后端 pytest 通过、前端 `npm run build` 通过、README 状态更新。
- 不破坏 M1 已交付接口与页面行为；保持现有视觉风格（深色侧栏 + 浅色内容，主色 `#0f766e`）。

### 0.9 M1 完成时的已知限制（历史记录）

- 商品 / SKU / 竞品 / 诊断均无写接口与工作台 UI。
- 系统配置页与导入中心是占位页（`UnderConstruction`）。
- 无 LLM 调用、无任务队列、无素材审核、无投放与复盘功能。
- 前端打包体积约 1.1MB（AntD 未分包），M6 视情况做 manualChunks。

  - `洁净洗衣 · 上门取送`，品类「洗衣服务」；套餐为洗鞋 ¥29/双、羽绒服清洗 ¥49/件、四件套清洗 ¥69/套，满 ¥99 上门取送免运费；阶段为「创意就绪」，预置 3 组获客方案 + 3 套分镜。

**服务配置（`SERVICE_PROFILES`）**

后端集中维护，至少包含：

| 字段 | 说明 |
| --- | --- |
| `category` | 服务品类白名单键，如「除甲醛服务」「洗衣服务」 |
| `price_unit` | 价格单位：`元/㎡`、`元/件起` |
| `persona / needs / scenarios` | 诊断与创意的目标人群、需求、场景 |
| `packages` | 服务套餐名称、计价方式、说明 |
| `trust_points` | 检测报告、复检、质保、上门取送等信任点 |
| `ctas` | 预约检测、领取方案、团购券、预约取送等转化动作 |
| `visual_template` | SVG 素材模板标识 |
| `forbidden_claims` | 品类禁用词与替代口径 |

- 商品列表 / 详情接口派生返回 `is_service`、`price_unit`，前端据此切换「服务」标识、价格单位与库存栏；不在数据库新增字段。
- 未命中白名单的品类继续走现有实物商品逻辑，不报错。

**服务 SKU 语义**

- 服务套餐仍存 `skus.spec_json`，至少包含套餐名、计价单位、服务范围 / 时效等键。
- 服务 SKU 库存自动填足（如 9999）、`warn_threshold=0`；大盘与店铺的库存预警查询必须排除服务品类 SKU。
- 服务商品前端隐藏库存、安全库存、调整库存、库存流水；新建 / 编辑 SKU 时隐藏库存输入，由系统补默认值。
- 平台映射、竞品、诊断、创意、素材、任务能力保留，不单独建立服务套餐表。

**诊断、创意与素材**

- 诊断 Mock 与真实提示词按 `SERVICE_PROFILES` 注入服务人群、场景、套餐、信任点与合规口径。
- 创意 Mock 与真实提示词按品类生成服务化方案，仍满足 ≥3 组获客方案、≥3 套脚本、每套 ≥4 镜。
- 服务商品在创意 Tab 使用「获客素材方案」表述；方案字段结构不变，继续支持在线编辑、确认、归档。
- SVG 模拟素材按品类切换模板：除甲醛为洁净空气 / 检测质保，洗衣为衣物洗护 / 上门取送；素材标签使用「获客素材」，并固定标注「模拟生成，仅供方案评审」。

**合规文案边界**

- 除甲醛禁用「零甲醛」「100% 去除」「永久有效」；统一使用「检测数据说话、按空间定制方案、复检与质保」。
- 洗衣禁用「100% 洗净」「绝对不伤衣」；统一使用「按面料标识洗护、异常件先沟通、超时赔付按门店规则」。

**本次边界**

- 不改表结构，不新增服务区域、预约时段、服务容量等独立字段；这些能力在 M4 投放建议中按需评估。
- 不接入真实本地生活广告接口；投放仍只输出建议并人工确认。
- 不改变实物商品的既有接口、页面与种子阶段。

## 2. M2 —— 商品建档、SKU 库存、竞品与智能诊断

### 目标

打通闭环第一阶段：店铺 / 商品 / 多规格 SKU / 平台映射 / 竞品录入与解析 / 结构化诊断生成与编辑。

### 后端任务

1. **店铺管理**
   - `POST /api/stores`（manager）、`PUT /api/stores/{id}`（manager，维护 auth_status / auth_ref）。
   - 店铺名、平台、授权状态校验；auth_ref 只存脱敏标识。
2. **商品 CRUD**
   - `POST /api/products`、`PUT /api/products/{id}`、`POST /api/products/{id}/archive`。
   - 校验：名称必填、store 存在、价格带 min ≤ max、main_sku 必须属于该商品。
3. **SKU 与库存**
   - `POST /api/products/{id}/skus`、`PUT /api/skus/{id}`、`DELETE /api/skus/{id}`。
   - `POST /api/skus/{id}/stock-adjust`：参数 `change`、`reason`，更新库存并写 `stock_flows`。
   - `GET /api/skus/{id}/stock-flows`。
4. **平台规格映射**
   - `GET/POST /api/skus/{id}/mappings`、`PUT/DELETE /api/mappings/{id}`。
5. **竞品**
   - `GET/POST /api/products/{id}/competitors`、`PUT/DELETE /api/competitors/{id}`。
   - `POST /api/products/{id}/competitors/parse`：入参为粘贴文本，走 LLM 双通道抽取结构化参数，返回**草稿**（`source=ai_parse`、`parse_status=draft`），人工校对后保存。
6. **LLM 双通道服务**
   - 新建 `app/services/llm.py`：统一 `generate_structured(task_type, context) -> dict`。
   - 读取 `system_configs["llm"]`：`mode`（mock/real）、`base_url`、`api_key`、`model`、`temperature`、`timeout_seconds`。
   - 真实通道优先支持 Anthropic Messages API（环境已有 `ANTHROPIC_BASE_URL` / `ANTHROPIC_AUTH_TOKEN`），并保留 OpenAI 兼容配置能力；Mock 通道必须产出同样结构的中文内容。
   - 输出必须经过 Schema 校验；真实通道失败时可回退 Mock，并在响应中标注实际使用的通道。
   - 不记录 API Key 明文日志。
7. **诊断**
   - `POST /api/products/{id}/diagnoses/generate`，可选 `source_report_id`。
   - `GET /api/products/{id}/diagnoses`（版本列表）、`GET /api/diagnoses/{id}`、`PUT /api/diagnoses/{id}`（编辑当前版本内容）。
   - 每次生成版本号自增，旧的置 `history`，新的置 `current`。
   - `content_json` 必须包含：`audience`、`price_analysis`、`selling_points`（矩阵）、`conversion_blockers`、`optimization_directions`。
   - 生成上下文：商品信息、SKU 价格带、竞品参数、上一轮复盘行动项（如有）。
8. **测试**
   - 库存调整与流水、诊断版本递增、编辑内容、竞品解析草稿、manager 专属店铺接口 403。

## 4. M4 —— 投放实验审批、经营数据回填与闭环复盘
